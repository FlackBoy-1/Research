# Журнал исследования (НИР)

**Тема:** Исследование методов оптимизации размерности латентно-семантического пространства в задачах обработки текстовых сообщений в условиях чрезвычайных ситуаций.

## 1. Рабочая гипотеза
Существует такое количество латентных осей (k*) и такой объём словаря лемм (V*), при которых латентно-семантическое пространство (LSA) сохраняет достаточную семантическую адекватность для передачи смыслов в домене «туризм/ЧС». При этом размерность пространства и объём словаря существенно сокращаются по сравнению с полным набором, что снижает вычислительную сложность и требования к каналам передачи данных.

## 2. Методология
- **Метод:** LSA (Latent Semantic Analysis) с использованием усеченного сингулярного разложения (TruncatedSVD).
- **Задача:** Эмпирический поиск k* (число компонент) и V* (объём словаря лемм).
- **Оценка (обновлено 2026-10-22):** Четыре независимые метрики:
  1. `F1_intent` (Macro) — по интентам. Основная метрика.
  2. `F1_urgency` (Macro) + `MAE_urgency` — по 4 уровням urgency. MAE — вспомогательная (порядковая шкала).
  3. `F1_joint` (Macro по парам (intent, urgency), `min_support = 10`) — согласованность осей. Анализ чувствительности при `min_support = 5` — в приложении, не в основной таблице. Комбинации с support < 10 исключаются и перечисляются в отчёте.
  4. `F1_urgency_on_SOS` (Macro) — доменная метрика «цена ошибки»: urgency только на строках с intent = SOS.

  «Общий F1» как среднее `F1_intent` и `F1_urgency` **не используется** (несопоставимость номинальной и порядковой шкал). Обоснование `min_support = 10`: при support < 10 Macro F1 по комбинации — шум (одна ошибка меняет метрику на 10+ п.п.); 95% ДИ при n=5 покрывает почти весь диапазон [0,1], при n=10 — уже нет.
- **Схема:** Двухпроходная. Сначала k* на полном словаре, затем V* при фиксированном k*.

## 4. Зафиксированные правила

1. **КМСА:** Не сворачивается в одно число. Задаётся правило «плато» по каждой из трёх метрик отдельно.
2. **Правило выбора k\*:** При расхождении локтей по трём метрикам — приоритет у F1. Проверка: ошибка восстановления не превышает минимум более чем на 5%, силуэт не падает ниже 0.1. Если не проходит — сдвиг вправо до первого k, где все три метрики в «зелёной зоне». В крайнем случае — максимум F1 с явной пометкой.
3. **Двухпроходная схема:** Сначала k* на полном словаре, потом V* при фиксированном k*. При смене словаря SVD обучается заново с нуля (матрицы несовместимы, перенос модели не делается).
4. **Экспертные пары:** На отдельном наборе, не пересекающемся с train и hold-out. Если реальный корпус < 800 строк — переключение на размещение экспертных пар только на train.
5. **Синтетика:** Не попадает в hold-out, помечается колонкой `is_synthetic`.
6. **OOV:** Неизвестные слова заменяются на `[UNK]` до векторизации. `[UNK]` включается в словарь V*.
7. **Порог сохранения смысла:** Определяется эмпирически на основе экспертных оценок. Универсальная числовая константа не используется.
8. **Библиотека лемматизации:** Изначально планировалась Natasha, однако в связи с её несовместимостью с актуальными версиями Python (и невозможностью использовать форк mawo-natasha для морфологии), принято решение использовать pymorphy3. Это современный, стабильный форк pymorphy2, обеспечивающий корректную лемматизацию без внешних моделей. (Обоснование см. в разделе 6).
9. **Scree Plot:** Строится по `singular_values_`. `explained_variance_ratio_` выводится в отчёт отдельно, для поиска локтя не используется.
10. **Поиск локтя:** Библиотека `kneed`, параметры по умолчанию (S=1.0, interp_method='interp1d'). При отсутствии локтя — перебор S в диапазоне 0.5–2.0 с визуальной проверкой.
11. **Интерпретация осей:** Топ-10 лемм по весу на ось. Формулировки помечаются как «интерпретация исследователя».
12. **Определение категории SOS:** Категория SOS присваивается только сообщениям, содержащим прямой призыв о помощи (просьбы, требования, императивы: «помогите», «спасите», «вызовите спасателей»). Сообщения, констатирующие факт опасности (например, «начался камнепад», «сдуло палатку»), даже если они описывают угрозу жизни, относятся к категории Информационное, если в них нет прямого запроса на спасение. Это правило введено для четкого разделения намерения (intent) и тональности/степени угрозы.
13. **Структура категорий (таксономия):** На этапе пилота принято решение оставить 4 верхнеуровневые категории: SOS (призыв о помощи), Информационное (констатация фактов, статусы), Запрос (вопросительные сообщения, требующие информации) и Тест (проверка связи).
Примечание: Если на этапе валидации (Этап 6) окажется, что класс Запрос слишком мал (менее 50 сообщений в итоговом корпусе) или плохо отделяется от Информационное, классы будут объединены, и модель будет переобучена.
14. **`case_id` (группировка перефразов).** В корпус вводится столбец `case_id`. Строки, являющиеся перефразами одного сценария, получают одинаковый `case_id`. Для остальных строк `case_id = id`. Дедупликация корпуса **не производится**: число сообщений ≠ число сценариев, это фиксируется в выводах. `case_id` используется **только** для группировки при формировании hold-out (перефразы одного кейса не разносить в train и test).
15. **Hold-out (уточнение правила 4).** Hold-out = 20% **не-синтетических** строк, без разнесения перефразов одного `case_id` в train и test. На текущем этапе hold-out **не зафиксирован** (столбец `is_holdout` = 0 у всех строк); фиксация будет выполнена после расширения корпуса. В `08_validation.py` используется `train_test_split` с группировкой по `case_id`; после фиксации hold-out — чтение `is_holdout`.
16. **Таксономия интентов (обновление раздела 5.3).** Добавляются интенты:
   - `техногенная_угроза` — техногенные аварии, пожары, утечки, обрушения, радиация.
   - `статус_группы` — сообщения «всё хорошо / идём по плану / на месте» (для группы и для одного человека).
   - `погибший` — факт смерти (приоритет над причиной: «погибли от переохлаждения» → `погибший`, а не `погода`).
17. **`позиция` (уточнение).** `позиция` — только сообщение о местоположении (координаты, «я на перевале», «вышли к озеру»). Сообщения «всё хорошо, идём по плану» → `статус_группы`. Оба интента остаются в категории `Информационное`.
18. **`проверка_связи` (уточнение).** Интент `проверка_связи` всегда относится к категории `Тест` (строка 50 правится с `Информационное` на `Тест`).
19. **`заблудился` vs `потерялся` (уточнение правила 5.2).** `заблудился` — субъект потерял ориентир (тропу, лагерь, направление). `потерялся` — субъект потерял **другого** (человека, группу). Строки 762, 764, 765, 771, 772, 776 → `заблудился`; 768, 838 → `потерялся`.
20. **`urgency` — отдельная задача.** `urgency` предсказывается **отдельным классификатором** (вариант A). Шкала 5.1 сохраняется. В журнале фиксируется: «F1 по urgency ожидается ниже, чем по intent, из-за порядковой природы шкалы и размытости границы 3 vs 4; это не является дефектом модели».

## 5. Уточнения таксономии и лингвистические правила (обновлено 2026-10-22)

 **5.1.** Шкала срочности (urgency)
В ходе пилотной разметки принято решение расширить стандартную шкалу срочности до 4 уровней для более точной градации угроз:
*   `1` — Тест / неважное сообщение (проверка связи, плановые статусы).
*   `2` — Важное сообщение (запросы информации, уточнения маршрута, незначительные поломки).
*   `3` — Потенциальная угроза жизни (заблудились, заканчиваются ресурсы, ухудшение погоды).
*   `4` — Прямая угроза жизни (лавина, нападение, сильное кровотечение, срочная эвакуация).

 **5.2.** Семантическое разграничение состояний
Зафиксировано принципиальное лингвистическое различие для корректной классификации:
*   **`заблудился`** — субъект потерял ориентир (потерялся сам).
*   **`потерялся`** — субъект потерял другого человека (членов группы, спутников).

 **5.3.** Глоссарий интентов (для пилотного корпуса)
Для единообразия разметки зафиксирован следующий список допустимых интентов:
*   `заблудился` — потерял ориентир.
*   `потерялся` — потерял другого человека.
*   `травма` — физический ущерб здоровью (перелом, кровотечение, обморожение, болезнь).
*   `природная_угроза` — лавина, камнепад, пожар, сель.
*   `техногенная_угроза` — техногенные аварии, пожары, утечки, обрушения, радиация.
*   `животная_угроза` — нападение или присутствие опасного животного.
*   `нет_припасов` — закончилась вода, еда, медикаменты, газ.
*   `техническая_неисправность` — сломалось или разрядилось оборудование.
*   `погода` — ухудшение погодных условий (туман, ветер, снегопад).
*   `позиция` — сообщение о текущем местоположении.
*   `статус_группы` — сообщения «всё хорошо / идём по плану / на месте» (для группы и для одного человека).
*   `погибший` — факт смерти (приоритет над причиной).
*   `проверка_связи` — тестовые сообщения, запросы подтверждения.
*   `запрос_маршрута` — вопросы о том, как пройти.
*   `запрос_погоды` — вопросы о прогнозе погоды.
*   `запрос_информации` — прочие вопросы (где вода, контакты спасателей, как развести огонь).

**Примечание:** При масштабировании корпуса (более 800 строк) список может быть расширен, однако все новые интенты должны быть задокументированы в этом журнале до начала разметки.
